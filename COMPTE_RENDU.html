Pourquoi certains tests attendant un code 422 passaient-ils déjà alors que rien n'était encore codé ?

Le schéma Livraison était configuré avec model_config = ConfigDict(extra="forbid") et n'avait aucun champ déclaré (seul distance_km était présent). Dès lors, tout champ transmis dans la requête HTTP était considéré comme inconnu et interdit, provoquant systématiquement un rejet automatique par Pydantic avec une erreur 422 Unprocessable Entity. Les tests attendant 422 réussissaient donc par « faux vert » car tout était rejeté, y compris les données légitimes.

3. Implémentation de la fonction predict()

@app.post("/v1/predict", response_model=PredictionOut)
def predict(livraison: Livraison):
    predictor = state.get("predictor")
    if predictor is None:
        raise HTTPException(
            status_code=503,
            detail="Modèle non chargé. Veuillez vérifier la présence du modèle ou ré-entraîner avec python -m logiai.train"
        )
    resultat = predictor.predict(livraison.model_dump())
    return PredictionOut(**resultat)

5. Questions de compréhension

  1. Pourquoi charge-t-on le modèle au démarrage et pas à chaque requête ?
    Le chargement depuis le disque et la désérialisation du modèle (joblib) prennent des dizaines à centaines de millisecondes et sollicitent fortement le CPU/disque. Le charger une seule fois au démarrage (cycle lifespan) et le garder en mémoire RAM permet d'exécuter chaque prédiction en quasi-instantané (< 2 ms).
  2. Qui écrit le contrôle « pluie <= 100 » (ou 300), et où est-il écrit ?
    Le développeur l'écrit dans logiai/api/schemas.py via le paramètre le=... de Field(). FastAPI et Pydantic interceptent et exécutent automatiquement cette validation avant tout traitement applicatif.
  3. Différence entre 422 et 503 ?
    Le code 422 correspond à une erreur client (données envoyées erronées ou non conformes). Le code 503 correspond à une erreur serveur (le serveur est fonctionnel mais sa dépendance d'inférence est temporairement indisponible).
  4. Pourquoi une route /v1/predict plutôt que /predict ?
    Le versionnement d'API garantit la rétrocompatibilité : on peut déployer plus tard une /v2 sans impacter ni casser les clients existants qui continuent de consommer la version 1.
  5. Que se passerait-il si la distance était déclarée int ?
    Toute distance contenant une valeur décimale (ex. 14.8 km) provoquerait une erreur de validation 422 ou une troncature forcée, privant l'API d'une précision kilométrique réelle.

6. Décision de conception : Modèle absent

Répondre 503 ou refuser de démarrer ? Qu'est-ce que chaque option fait perdre ?

  • Option A (Répondre 503) : L'API démarre et l'endpoint /health indique {"status": "ok", "model_loaded": false}. Les dashboards de supervision peuvent identifier immédiatement la cause sans que le serveur ne tombe en panne complète. La documentation /docs reste également consultable. Ce qu'on perd : Les requêtes d'inférence échouent pour les utilisateurs.
  • Option B (Refuser de démarrer) : Philosophie « fail-fast » où un orchestrateur (Kubernetes) ne dirigera aucun trafic vers un conteneur non opérationnel. Ce qu'on perd : Toute observabilité immédiate via /health ou /docs, provoquant des boucles de redémarrage (CrashLoopBackOff).

Une application mobile (iOS/Android) ou web en React n'a besoin que d'effectuer une requête HTTP POST standard, sans nécessiter d'environnement Python ni télécharger un modèle lourd.
